## Phase 1：Problem Framing（问题重构 — 发散）

### 1.1 用故事重述问题

> **一位短剧编剧**，在拿到网络小说 IP 后，需要把 **50 章小说改成剧本格式**。她现在的方法是：打开 Word，一边读小说一边手动改写——每章要花 2-4 小时。最痛苦的不是打字，而是 **改到第 10 章时忘了第 3 章的细节**，角色名字写串、情节前后矛盾、格式忽左忽右。她试过用 ChatGPT，但每次要重新贴文本、重复解释格式，上下文一断就又乱了。

### 1.2 HMW 五方向拆解

| 方向 | 说明 | HMW 问题 |
|------|------|----------|
| **否定** | 如何让用户放弃这个需求？ | HMW 让创作者不再需要手动改写小说为剧本？ |
| **积极** | 如何让用户自己就能解决？ | HMW 让创作者自己能一键完成小说→剧本转换？ |
| **转移** | 如何让其他人/物来解决？ | HMW 让 AI 承担格式记忆和跨章一致性，而非让创作者记住？ |
| **脑洞大开** | 完全不敢想的方案 | HMW 让多个 AI Agent 像编剧团队一样协作改编？ |
| **分解** | 把大问题拆成小步骤 | HMW 把改编拆成：角色档案→结构分析→逐章改写→摘要记忆→质量自检？ |

### 1.3 HMW 质量自检

| HMW | 空泛？ | 过于具体？ | 可控？ | 判定 |
|-----|--------|-----------|--------|------|
| 否定方向 | ✅ "不再手动改写" | ✅ | ✅ | **通过** |
| 积极方向 | ✅ "一键转换" | ✅ | ✅ | **通过** |
| 转移方向 | ✅ "AI 承担一致性" | ✅ | ✅ | **通过** |
| 脑洞方向 | ✅ | ✅ | ⚠️ Multi-Agent 成本高 | **暂缓** |
| 分解方向 | ✅ | ✅ | ✅ | **通过** |

**选出 3 个最优质 HMW**：**积极方向** + **转移方向** + **分解方向** → 进入 Phase 2。

## Phase 2：Solution Generation（方案生成 — N×4×4）

以 **HMW-积极方向**（一键转换）为主线，融合 **转移方向**（AI 承担记忆）和 **分解方向**（Pipeline 拆解）。4 角色 × 4 轮头脑风暴：

### 第 1 轮：产品经理视角

| # | 方案卡 | 反对理由 |
|---|--------|----------|
| 1 | **一键改编全部章节** — 上传后自动对所有章节执行改编，后台排队处理，前端轮询进度 | 长篇小说可能烧几十块 API 费用；用户中途想停止怎么办？ |
| 2 | **角色自动提取+持久化** — 首次上传后，AI 自动扫描前几章提取角色档案，存入 DB，后续改编时自动注入 | 角色别名识别不准怎么办？网文中同一个人有 3-5 个称呼 |
| 3 | **跨章记忆摘要链** — 每章改编完成后生成结构化摘要，传给下一章作为"前情提要" | 摘要可能丢失关键信息；累积摘要越来越长导致 token 消耗增长 |
| 4 | **风格切换** — 同一本小说支持一键切换三种剧本风格，无需重新上传 | 三种 Prompt 都要调优；漫画和舞台使用频次远低于影视 |

### 第 2 轮：开发工程师视角

| # | 方案卡 | 反对理由 |
|---|--------|----------|
| 5 | **DeepSeek 适配器** — 新增 `_call_deepseek()`，API 兼容 OpenAI 格式，成本降低 80% | DeepSeek 有时不稳定；并发限制严格；长文本理解可能不如 Claude |
| 6 | **长章节智能切分** — 超过 8000 字的章节在段落边界切分，带 overlap 上下文 | overlap 处可能产生重复内容；拼接处可能断裂 |
| 7 | **异步 BackgroundTasks 编排** — 用 FastAPI BackgroundTasks 而非 Celery，降低部署复杂度 | 服务重启丢失进行中任务；无重试机制；不能分布式扩展 |
| 8 | **SQLite + aiosqlite** — 零配置数据库，单文件存储，适合 Demo 和本地使用 | 并发写入性能差；不能用于多用户生产环境 |

### 第 3 轮：用户视角

| # | 方案卡 | 反对理由 |
|---|--------|----------|
| 9 | **示例小说一键加载** — 用户无需自己准备文件，点一个按钮就能加载预置示例 | 示例小说选什么？太长的体验慢，太短的看不出效果 |
| 10 | **拖拽上传 + 实时进度** — 拖拽文件上传，解析/改编进度可视化 | 进度展示需要后端配合增加状态粒度；轮询频率高增加服务器负担 |
| 11 | **三格式导出** — Markdown / TXT / DOCX 一键下载 | DOCX 格式复杂，短章节分页体验差 |
| 12 | **中文剧本阅读器** — 前端做语法高亮：场景标题/舞台指示/对白分类着色 | 纯前端正则解析，LLM 输出格式不对时高亮失效 |

### 第 4 轮：设计师视角

| # | 方案卡 | 反对理由 |
|---|--------|----------|
| 13 | **两栏布局** — 左章节列表（带状态圆点），右剧本阅读器 | 移动端无法用两栏；长章节列表滚动后右侧不跟随 |
| 14 | **Prompt 增强 + 反幻觉** — 强制格式约束、反幻觉指令、角色外貌标注 | Prompt 越长 token 消耗越大；过于严格可能抑制创造力 |
| 15 | **质量自检 + Warning** — 改编完成后自动检查格式规范，不合格标记 warning | 规则检查太机械；只能检测表面格式问题 |
| 16 | **风格切换 UI** — 项目详情页增加电影/漫画/舞台切换按钮 | 切换后需要重新改编才能生效，用户可能误以为切换即生效 |

#### 方案 #2 — 角色自动提取 + 持久化

| 维度 | 内容 |
|------|------|
| **方案描述** | 小说上传解析完成后，后台自动调用 `extract_characters()` 分析前 2-3 章，将角色写入 Character 表。后续每章改编时注入角色上下文 |
| **解决的用户问题** | "改到第 10 章时，主角的名字写成了配角的名字" |
| **目标用户** | 批量改编超过 3 章的所有创作者 |
| **预计工作量** | **M**（~1h）：upload.py 加后台任务 + chapters.py 格式优化 |
| **技术风险** | **中**：LLM 可能漏提取或误提取角色；网文别名多 |
| **优点** | ✅ `extract_characters()` 已实现只需接线；✅ DB 持久化支持人工修正；✅ 每章 token 几乎不增加 |
| **缺点** | ❌ 仅分析前 2-3 章，后期新角色不会自动追加；❌ 角色关系未提取 |
| **可复用代码** | `ai_adapter.extract_characters()` 已实现、`Character` 表已有完整字段、`_run_adaptation()` 中 character_context 构建逻辑已存在 |
| **与竞品差异** | Toonflow 用资产库硬约束角色（需人工录入），本方案用 AI 自动提取 + 人工可选修正 |
| **MVP 边界** | 仅提取前 3 章角色，不追踪关系，不支持中途追加 |
| **Kill Criteria** | 提取准确率 < 60%，或每次提取超过 30 秒 |
| **推荐度** | ⭐⭐⭐ **强烈推荐** — Demo 质量提升最大、实施成本最低的方案 |

#### 方案 #3 — 跨章摘要链记忆

| 维度 | 内容 |
|------|------|
| **方案描述** | Chapter 表新增 `chapter_summary` + `cumulative_summary`，每章改编后生成结构化摘要（新角色/状态变化/关键事件/悬念），累积传给下一章 |
| **解决的用户问题** | "改到第 10 章时忘了第 3 章的情节，前后矛盾" |
| **目标用户** | 改编超过 5 章的长篇创作者 |
| **预计工作量** | **S**（~30min）：models 加 2 字段 + ai_adapter 加 1 方法 + chapters.py 加 2 调用 |
| **技术风险** | **低**：摘要可能丢失细节，但比当前"只传 500 字尾巴"好得多 |
| **优点** | ✅ 极低成本（每章 ~800 token ≈ ¥0.002）；✅ 无外部依赖；✅ 累积摘要 token 增长可控 |
| **缺点** | ❌ 纯文本摘要无法精确查询；❌ 摘要质量依赖 LLM 理解能力 |
| **可复用代码** | Chapter 表现有字段结构、`ai_adapter.adapt_chapter()` 的 user_message 拼接逻辑 |
| **与竞品差异** | Alibaba Cloud 用 10 维评分做质量闭环，本方案用摘要链做记忆闭环，互补 |
| **MVP 边界** | 不做向量检索、不做摘要版本管理、不做摘要质量评估 |
| **Kill Criteria** | 摘要生成超过 10 秒，或累积摘要超过 2000 字符 |
| **推荐度** | ⭐⭐⭐ **强烈推荐** — S 级工作量，解决 Demo 最大的连贯性问题 |

| **推荐度** | ⭐⭐ **推荐** — 成本低但价值有限；时间紧迫可砍 |
